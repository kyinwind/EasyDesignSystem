# EasyDesignSystem 按钮组件需求分析

日期：2026-09-20
前置文档：`20260920按钮组件盘点报告.md`
状态：**待讨论确认**（确认后再进入技术方案设计与开发计划）
本文档只做需求分析与架构对齐，不含实现细节。

---

## 一、目标

把按钮从「4 个散装视觉样式的枚举」升级为「一份可组合实现 + 分层语义封装」，使按钮在 EDS 内部**风格统一、种类收敛、可扩展**，对上层**易用、可自封装、可精细控制**。

不追求"按钮种类更多"，追求**组合能力更完整 + 实现只有一份**。

---

## 二、架构决策（杨哥 2026-09-20 已确认）

### 2.1 分层结构

```
App 业务代码
  ├─► 易用层 1 · 分量优先（一维）      ← 调用方说「我要多重」
  ├─► 易用层 2 · 意图优先（一维）      ← 调用方说「我要干什么」
  └─► 实现层 · 三维原语（直接使用）    ← App 有自己的设计语言时走这条
          ↓
      实现层 emphasis × tone × size
          ↓
      Token 层 EDSDesignTokens
```

**核心约束：全包只有一份按钮样式实现。** 两层易用 API 都只是「一维入参 → 多维参数」的映射糖，不含任何独立的视觉代码。

这一条是整个方案的价值所在。现在的 4 个 ButtonStyle 是 147 行四份复制；改造后必须收敛为 1 份，否则"统一风格"的目标从第一天就失败了。

### 2.2 与 EDS 现有哲学的衔接

本方案不是新框架，而是把 EDS 已有的两层哲学延伸到按钮：

| EDS 已有 | 适用场景 | 本方案的对应物 |
| --- | --- | --- |
| Easy API（`.easyDesign(...)`） | 组合容器语义（Page / Section / Card） | **不涉及** |
| 精细 API（组件 + Token） | 特殊布局、定制页面 | 拆分成本文的「易用层」+「实现层」 |

⚠️ **命名提醒**：EDS 的 "Easy API" 已经是 `.easyDesign()` 的专有名词，且 README 明确写着「Easy API 不定义 `.button` 这类叶子样式」。因此本文的两层封装**不能叫 "Easy API"**，建议命名为「语义预设层」或「Semantic Presets」，并在 README 补一句澄清，避免读者把两者混淆。

## 三、待确认的核心问题：两套一维 API 的词汇表怎么划

这是本方案唯一有真实设计风险的地方。若处理不当，两套 API 会因为语义重叠而变成冗余负担。

### 3.1 风险：词汇表撞车

现有 `EDSButton.Role` 的值是 `.primary` / `.secondary` / `.soft` / `.danger`。

| 值 | 实际表达的是 |
| --- | --- |
| `.primary` / `.secondary` / `.soft` | **视觉分量** |
| `.danger` | **业务语义** |

如果两套易用层各自"再起一套名字"，极可能出现同一批概念被两套词汇分别命名（例如一层叫 `.soft`、另一层叫 `.secondary`），调用方无法建立稳定心智，维护面翻倍。**这是必须避免的。**

### 3.2 建议方案：两套词汇分工不重叠

| | 易用层 1 · 分量优先 | 易用层 2 · 意图优先 |
| --- | --- | --- |
| 参数名 | `role:`（沿用现名，降低迁移成本） | `intent:`（新参数名） |
| 词汇性质 | **纯视觉词**（只回答"多重"） | **纯场景词**（只回答"什么操作"） |
| 建议词表 | `.filled` `.outline` `.soft` `.plain` | `.destructive` `.confirm` `.dismiss` `.more` |
| tone 行为 | 固定为 `.accent`（正常操作） | 由语义决定（见下表） |
| 覆盖场景 | 正常操作的轻重选择 | 破坏性 / 确认 / 撤销 / 次级入口 |

意图词表的映射约定（emphasis 由设计系统决定，调用方不必思考）：

| intent | 映射为 (emphasis, tone) | 典型场景 |
| --- | --- | --- |
| `.destructive` | (filled, danger) | 删除确认对话框里的主操作 |
| `.confirm` | (filled, success) | 确认收货、通过审批 |
| `.dismiss` | (plain, neutral) | 取消、关闭、稍后再说 |
| `.more` | (plain, accent) | 卡片右上角「更多」、行内「编辑」 |

**意图词表故意只做 4 个。** 意图枚举是最容易膨胀的一类枚举，一旦开口就会有人往里塞 `.export` `.import` `.share`，最终变成第二套无法收敛的角色表。若某个操作找不到匹配的意图，正确做法是用易用层 1 或直接上三维，**不是加词**。

### 3.3 兼容与旧 API 的处置（需一并确认）

现存的 `EDSButton.Role`（`.primary` / `.secondary` / `.soft` / `.danger`）与旧代码的关系，有两个选项：

| 选项 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A · 冻结兼容**（推荐） | 保留 `Role` 与 4 个 ButtonStyle，标注 deprecated，内部转发到新实现。不删、不加值、不再宣传 | 现有 App / README / Examples / Tests **零改动**；公开 API 检查不破 | 包内长期存在一个"旧入口" |
| B · 直接替换 | 让 `role:` 复用为易用层 1 的参数名，旧值改名为 `.filled/.outline/.soft/.plain` | API 面更干净 | **破坏性变更**，所有宿主需改代码，与 EDS「0.2.x 起零破坏」的既有约定冲突 |

选项 A 的风险需明确：若同时保留「旧 `role:`（含 `.primary/.danger`）」与「新 `role:`（含 `.filled/.plain`）」，**同一个参数名会有两套值名**，这是不可接受的。因此若选 A，新易用层 1 的参数名需与旧 `role:` 区分开（例如 `emphasis:` 直接沿用实现层的参数名），或旧 `Role` 也保留在同一个 `role:` 参数上但标 deprecated。

**这一处需要杨哥明确选择，是本文档最关键的一个待决项。**

## 四、App 自封装需要满足的条件

杨哥提出「App 有自己的风格设计可以自己封装」。要真正支持这一点，实现层必须满足：

| 条件 | 原因 |
| --- | --- |
| 三维类型全部 `public` | 否则 App 拿不到参数类型，无法传值 |
| 三维类型 `CaseIterable` | App 可遍历生成自己的组件画廊 / 文档 |
| 三维类型 `Sendable` + `Hashable` | App 可存为常量、做缓存、在并发场景传递 |
| 提供 `EDSButtonStyle`（SwiftUI `ButtonStyle` 公开实现） | App 若用自己的 `Button` 容器，仍可套用 EDS 外观 |
| 提供 `EDSButtonAppearance` 值对象 | 承载解析结果，App 可读取颜色/尺寸做二次加工 |

典型自封装形态（实现层必须是 public 才能写出来）：

```swift
extension EDSButton where Label == Text {
    /// App 品牌主按钮
    static func brandPrimary(_ title: LocalizedStringKey, action: @escaping () -> Void) -> EDSButton<Text> {
        EDSButton(title, emphasis: .filled, tone: .accent, size: .medium, action: action)
    }
}
```

## 六、风格与色系需求（第二轮补充，2026-09-20）

### 6.1 杨哥的原话需求

- RightClickMate / TTSMate：主色蓝，偏**商务、正式**
- VideoHero：主色橙，偏**活泼**
- 期望：EDS 内置这两种色系的按钮风格（"就是我说的 easy api"）
- 其他 App 若有其他主色，可在**包外**定义自己的 easy api 来调用按钮组件

### 6.2 关键澄清：这是两个不同的轴，且现状差距巨大

必须先分清"色系"和"风格"，否则设计方向会错。

| | 色系（蓝 / 橙 / …） | 风格（商务正式 / 活泼轻快） |
| --- | --- | --- |
| 归属层 | Token 层的 `colors` | Token 层的 `radius` / `spacing` / `controlSize` / 动效 |
| 包里现状 | ✅ **已支持** | ❌ **完全缺失** |
| 使用入口 | `EDSTheme.shared.applyPreset(.orange)` | **没有入口** |

本次核查证据：

- **色系已支持**：`EDSPresetTheme` 已有 `.default`（#3185FF）/ `.blue` / `.orange`（#FF6B00）/ `.purple` 四个预设（`EDSTheme.swift:227-272`）。且 `edsTheme` 环境值惰性读取 `EDSTheme.shared.tokens`（`EDSThemeEnvironment.swift:14`），因此 `applyPreset` 之后按钮**立刻**跟随主题色。**"按钮跟随主色"这件事已经做完了，不需要新增按钮。**
- **风格完全缺失**：四个预设只改了 `colors` 和 `heroGradient`（`EDSTheme.swift:230-236 / 246-255 / 262-270`），`radius` / `spacing` / `controlSize` / 动效**全部沿用默认值**。而 `EDSDefaultTheme.json` 中只有 `radius {8,12,16,24}`、`controlSize.buttonHeight = 34`，**没有任何动效、描边、字重、按钮阴影 token**。

**结论：VideoHero 现在切橙色主题，按钮只是"变橙了的商务按钮"——圆角、高度、内边距、按压缩放、动效全都没变。** 所以缺的不是"两个彩色按钮"，而是**那根缺失的"风格轴"**。

### 6.3 必须避免的方向：把颜色做进按钮

若在包里内置"蓝色按钮"和"橙色按钮"两个按钮样式，会导致四个问题：

1. **按钮不再跟随主题** → 与 EDS 现有架构直接冲突（颜色归 Token 层，组件只负责映射）
2. **色系数量 = 按钮数量** → 以后新 App 用绿色就得在包里再加一个按钮样式。这正是"包外自己定义"要避免的事，但方向反了：应该在**主题层**扩展色系，而不是在**组件层**堆样式
3. **明暗外观无法适配** → 颜色目前以 hex 静态存储（`EDSColorTokens` 的 Codable 实现，导出 JSON 时统一按浅色外观解析），同一个"橙"在浅色/深色外观下需要不同取值；硬编码进按钮后失去调整空间
4. **破坏维度正交性** → 颜色是第三个正交维度。把它塞进按钮的角色枚举，等于把刚拆开的维度又粘回去

### 6.4 色系轴：现有能力核查（结论：够用，一次调用即可）

**下表是包里当前真实存在的 API，务必以此为准。**

```swift
// TTSMate / RightClickMate
EDSTheme.shared.applyPreset(.default)   // 蓝 #3185FF（= .blue）

// VideoHero
EDSTheme.shared.applyPreset(.orange)    // 橙 #FF6B00
```

> ⚠️ **文档修正**：本文档 §6.4 的上一版本写过 `EDSTheme.shared.apply(.businessBlue)` / `.livelyOrange`。那是**提案中的组合入口名，当前并不存在**，已作废。包里唯一可用的色系入口是 `applyPreset(_:)`（`EDSTheme.swift:148`），可选值为 `.default` / `.blue` / `.orange` / `.purple`。

**结论：色系这一半已经完成，不需要在包里新增任何按钮。** 调用方只需在 App 启动时调一次 `applyPreset`。

`applyPreset(.orange)` 之后按钮实际会变的颜色（逐项核查 `EDSButtons.swift`）：

| 按钮内部颜色 | 取值来源 | 是否跟随主题 |
| --- | --- | --- |
| primary 背景 | `colors.primary` | ✅ |
| secondary 描边 + 文字 | `colors.primary` | ✅ |
| soft 背景 | `colors.accentSoft`（= `accent.opacity(0.12)`，计算属性，`EDSDesignTokens.swift:107`） | ✅ |
| soft 文字 | `colors.primary` | ✅ |
| danger 背景 | `colors.danger` | ✅ |
| primary / danger 的文字 | **硬编码 `.white`**（`EDSButtons.swift:25 / 136`） | ❌ |
| 描边 1.5pt、圆角 `radius.md`、高 `buttonHeight`、压 0.97、动效 0.15 | 引 token 或魔数 | ❌（与颜色无关，属风格范畴） |

### 6.5 三个必须知道的边界（当前行为的准确描述，非缺陷）

**边界 1：启动时调用可靠；运行时动态切换不保证刷新。**

`edsTheme` 环境值惰性回退到 `EDSTheme.shared.tokens`（`EDSThemeEnvironment.swift:14`），但 `EDSTheme` 是普通 class 而非 `ObservableObject`，SwiftUI 无法感知其变化，**已渲染的视图不会自动重绘**。`EDSTheme.swift:45` 的注释亦明确写着"运行时动态切换主题暂不承诺自动刷新 UI"。

- App 启动阶段调一次 → ✅ **可靠**（视图首次渲染即读到正确颜色）
- 设置页让用户选主色并实时切换 → ❌ **不可靠**，需额外机制（`.id(themeID)` 强制重建，或把 `EDSTheme` 改造为 `@Observable`）

**边界 2：`applyPreset` 是整体替换而非合并，且对调用顺序敏感。**

`tokens = preset.tokens`（`EDSTheme.swift:149`），预设内部是 `EDSDesignTokens()` 默认构造 + 只改几个字段。后果：

- 先 `configure { }` 再 `applyPreset(...)` → **configure 的改动会被全部冲掉**
- 正确顺序：**先 `applyPreset`，再 `configure` 微调**

**边界 3：三个预设的语义色不一致。**

| 预设 | primary | success / warning / danger |
| --- | --- | --- |
| `.default`（=`.blue`） | #3185FF | **未设置** → 取 `EDSDesignTokens()` 默认值：`.green` / `.orange` / `.red`（系统色） |
| `.orange` | #FF6B00 | #27B15A / #F9B135 / #E54444 |
| `.purple` | #8B5CF6 | #10B981 / #F59E0B / #EF4444 |

即 `applyPreset(.default)` 下"删除按钮的红"是系统 `.red`，而 `.orange` 下是 `#E54444`——**两个 App 的删除红不是同一个红**。既成事实，是否统一留待技术方案中决策。

另：颜色以 hex 静态 sRGB 存储（`Color(hexRGB:)`），**不随浅色/深色外观切换**；而 `textPrimary` / `textSecondary` 用 `Color.primary` / `.secondary` 语义色，会自动适配。品牌色固定是合理取向，但需知晓此边界。

### 6.5.1 包外 App 自定义其他主色（当前即可用）

不需要 EDS 任何内部改动：

```swift
EDSTheme.shared.applyPreset(.default)          // 先选一个最接近的基础预设
EDSTheme.shared.configure { tokens in          // 再微调（注意顺序）
    tokens.colors.primary = Color(hexRGB: "#27B15A")
    tokens.colors.accent  = Color(hexRGB: "#27B15A")
}
```

（注意 `primary` / `accent` 的类型是 `Color`，不是 `String`——需用 `Color(hexRGB:)` 构造。）

### 6.6 风格轴：暂缓（杨哥 2026-09-20 决议，已确认）

原始提案与"商务 vs 活泼"差异表保留在 §6.7 作备案，**本阶段不实现**。理由：

1. 当前项目对包的需求尚未到达"需要风格变换"这一步
2. 风格轴属**锦上添花**，三维模型（D1）属**修硬伤**——优先级差一个量级
3. 风格轴会引入一批新 token（`radius.button` / `buttonHeights` / `stroke.buttonBorder` / `motion.*`）。在按钮实现层尚未收敛时铺开这些 token，等于在流沙上盖楼

**留的口子（重要）**：三维模型的 size 轴（D2）本身就会引入"高度 / 内边距 / 圆角"的可变参数。该能力一旦建成，风格轴所需的基础**已完成一半**——将来补风格轴的成本比现在预估的低。**本次不做，不会让未来变难。**

### 6.7 风格轴原始提案（备案，本阶段不实施）

**若将来引入风格轴，设计如下**（存档备查）：

```swift
EDSTheme.shared.applyPreset(.orange)        // 现有能力：色系
EDSTheme.shared.applyStyleProfile(.lively)  // 将来能力：风格档
```

**核心价值**：easy API 不需为每种风格各写一套——同一份按钮代码在商务蓝下稳重方正，在活泼橙下自动变圆角饱满：

```swift
// TTSMate / RightClickMate  →  EDSTheme.shared.applyStyleProfile(.business)
// VideoHero                 →  EDSTheme.shared.applyStyleProfile(.lively)
// 两边按钮代码完全一样，一行都不用改
EDSButton("开始处理", role: .filled) { }
```

风格档做成**公开可构造的值对象**，包外 App 可自由组合或自写一档：

```swift
public struct EDSButtonStyleProfile: Sendable, Hashable {
    public var cornerRadius: CGFloat
    public var height: CGFloat
    public var horizontalPadding: CGFloat
    public var borderWidth: CGFloat
    public var pressScale: CGFloat
    public var pressDuration: Double
    public var showsShadow: Bool

    public static let business: EDSButtonStyleProfile
    public static let lively: EDSButtonStyleProfile
}
```

"商务正式"与"活泼轻快"的候选差异项（**未经确认，仅供参考**）：

| 维度 | 商务正式（提案） | 活泼轻快（提案） | 涉及新增 token |
| --- | --- | --- | --- |
| 按钮圆角 | 6–8，方正利落 | 14+，饱满近胶囊 | `radius.button` |
| 按钮高度 | 32 | 38 | `controlSize.buttonHeights` |
| 横向内边距 | 16 | 20 | `controlSize.buttonPaddingH` |
| 字重 | semibold | bold | typography |
| 描边宽度 | 1 | 1.5–2 | `stroke.buttonBorder` |
| 按钮阴影 | 无 | 轻投影（浮起感） | `shadow.button` |
| 按压缩放 | 0.98，克制 | 0.94，明显 | `motion.pressScale` |
| 动效时长 | 0.12，干脆 | 0.20，柔和 | `motion.duration` |
| 图标与文字间距 | 4 | 8 | spacing |

## 十、第四轮方案评估：role 作为「预设别名」+ 三维参数（杨哥 2026-09-20 提案）

### 10.1 杨哥的提案原文（要点）

1. `EDSButton("确定", role: .primary)` 扩展为可填 `emphasis / tone / size / role`：只填 `role` 时，**一个 role 即代表一套固定的三维组合**（role 相当于 easy API）；也可以只填三维、不指定 role。
2. **新增一种 role**：表达"设置已完成、点击进去有内容"，背景为**浅绿色**。

### 10.2 结论：方案成立，而且比前两轮更务实。但有 2 处必须修正

#### 修正 1（Swift 语言层面，避不开）：不能是"一个 init 带四个参数"，必须拆成两个重载 init

杨哥写的是 `EDSButton("确定", emphasis, tone, size, role)`。这个形状在 Swift 里**没有合法实现**，三条路都堵死：

| 尝试 | 结果 |
| --- | --- |
| `role` 给默认值 `.primary` | `EDSButton("确定", emphasis: .soft, tone: .danger) {}` 会**隐含携带** `role = .primary`，出现两个真源：三维说"soft+danger"，role 说"filled+accent"。编译器不会报错，但行为取决于实现内部谁优先判定 → **隐性 bug 温床** |
| `role` 默认 `nil` | `EDSButton("确定") {}` 变得**无样式可渲染**，必须给"什么都没填"补一条兜底规则，等于把隐式契约塞进实现 |
| `role` 放在最后且给默认值 | 与旧签名 `init(_ title:, role:, systemImage:, action:)` **撞车**，编译器报 ambiguous |

**正确做法：两个平行的重载 init，由编译器按参数标签自动分流。** 这是 Swift 处理"同一类型两条调用路径"的标准手段：

```swift
// 路径 A（旧签名，原样保留，零改动）—— 语义预设
public init(
    _ title: LocalizedStringKey,
    role: Role = .primary,
    systemImage: String? = nil,
    action: @escaping () -> Void
)

// 路径 B（新增）—— 三维原语
public init(
    _ title: LocalizedStringKey,
    emphasis: Emphasis,            // ← 故意不给默认值，这是消歧义的关键一行
    tone: Tone = .accent,
    size: Size = .regular,
    systemImage: String? = nil,
    action: @escaping () -> Void
)
```

> **`emphasis` 为什么不给默认值？** 一旦给了，`EDSButton("确定") {}` 会同时匹配两个 init，Swift 直接报 `ambiguous use of init`。**这一行是本次改造最关键的技术细节，必须在动手前钉死。**

三条调用路径因此各自成立、互不干扰：

```swift
EDSButton("确定", role: .primary) { save() }                    // 路径 A：预设
EDSButton("忽略并删除", emphasis: .soft, tone: .danger) { }       // 路径 B：三维
EDSButton("确定", emphasis: .soft, tone: .danger, size: .small) { }  // 路径 B：三维 + 尺寸
```

#### 修正 2（概念层面，但让方案真正自洽）：`role` 的定位要从「维度」降级为「预设别名表」

杨哥说"role 相当于 easy API"——**理解正确**。但它有一个必须点明的推论：

> **`role` 从此不再是"一个维度"，而是一张"快捷方式对照表"。**

这个区别非常实际。§3.1 我曾警告"词汇表撞车"的风险：`.primary`（视觉词）与 `.danger`（语义词）并列在一个枚举里，从**维度**视角看是错的。但如果 `role` 的定位是**别名表**，混排就是**合理的**：

> 类比：CSS / Bootstrap 的 `.btn-primary` / `.btn-success` / `.btn-danger` 从来不在同一个维度上，但没人觉得有问题——因为它们不是"分类维度"，是"预设名字"。

**降级带来的三个实际好处：**

1. 新 role 可以叫任何名字，不受维度约束（`.done` 可以，`.success` 也可以）
2. 不再有"第 5 种 role 该归哪个维度"的纠结——**加一个名字就是加一行映射**
3. **§3.2 那套"两套一维词汇表"的复杂设计（D6）可以不做**——`role` 这一套已经足够充当 easy API。这正是杨哥说的"不用动干戈"

**代价（必须说清）：** 别名表会缓慢膨胀，每个真实场景都想再要一个名字。约束是——

> **新 role 必须对应"真实且重复出现的场景"，而不是"这个组合我没试过"。建议上限 8–10 条；超过就说明该用三维了。**

| --- | --- |
| `EDSButton("确定", role: .primary) { }` | ✅ 不变，走路径 A |
| `EDSButton(role: .danger) { label }` | ✅ 不变，旧 label init 原样保留 |

### 10.4 浅绿色「已完成」按钮：四个必须先解决的问题

#### 问题 1：包里没有"浅绿" token —— 但视觉语言已经存在

核查 `EDSColorTokens`（`EDSDesignTokens.swift:86-109`）：只有 5 个基础色（primary / accent / success / warning / danger）+ **1 个派生色** `accentSoft = accent.opacity(0.12)`。**没有 `successSoft`。**

但有个有用的发现：**`EDSBadge.Style.success` 已经实现了这个视觉**（`EDSButtons.swift:389/397`）——绿字 + 12% 浅绿底 + Capsule。**所以"浅绿底"在 EDS 里不是新东西，只是从来没给过按钮。**

→ 建议：新增 `successSoft` 派生计算属性，与 `accentSoft` 对称。一行代码，**不新增 JSON 字段**，不破坏主题文件兼容性。

#### 问题 2：浅绿底上的文字色，对比度不达标（真障碍，必须定）

| 文字色方案 | 表现 | `.default`（蓝）主题对比度 | `.orange` 主题对比度 |
| --- | --- | --- | --- |
| `colors.success` 绿字 | 与 `EDSBadge` 一致，语义最清楚 | 系统绿在浅绿底上 ≈ **2.2 : 1** ❌ | #27B15A ≈ **3.0 : 1** ⚠️ |
| `textPrimary` 近黑字 | 绿色只由底色承担 | ≈ 15 : 1 ✅ | ≈ 15 : 1 ✅ |
| 新增深绿 token | 绿字且可读 | 需要新 token | 需要新 token |

WCAG AA 正文要求 **4.5 : 1**。**结论：绿字方案在两个主题下都不达标。**

→ 建议：**`textPrimary` 字 + 浅绿底 + ✓ 图标**（图标承担语义，颜色不是唯一线索）。这同时满足 `accessibilityDifferentiateWithoutColor`——EDS 已经在 `EDSBadge` 里处理过这个无障碍开关（`EDSButtons.swift:356-372`），沿用同一策略即可。

#### 问题 3：`.default` 主题下"完成绿"是系统绿，与 `.orange` 主题的不是同一个绿

再次印证 §6.5 边界 3：`.default` 预设没有设 success / warning / danger。后果很具体：

> **同一个 `.done` role，在 TTSMate（蓝主题）下是系统绿，在 VideoHero（橙主题）下是 #27B15A。**

→ 需一并决策（D16）：是否在 `.default` 里补上 hex 语义色，让三个预设的语义色统一。这是一行改动，但影响面覆盖全部语义色组件（Button / Badge / 状态组件）。

#### 问题 4：与 `EDSBadge(.success)` 视觉撞车的可用性风险

如果"已完成"按钮做成"浅绿底 + 绿字 + 小胶囊"，它跟 Badge 长得几乎一样，用户会**误判为不可点击的状态标签**。

区分手段必须是**体量与交互反馈**，不是颜色：

| | `.done` 按钮 | `EDSBadge(.success)` |
| --- | --- | --- |
| 高度 | 跟随 size 档（28 / 34 / 44） | 小尺寸自适应（captionStrong + xxs 内边距） |
| 圆角 | `radius.sm` = 8 | **Capsule**（全圆角） |
| 交互 | hover 变暗 + 按压缩放 0.97 | **无** |

→ **这条必须靠 Examples 里并列展示来验收**：把 `.done` 按钮与 `EDSBadge(.success)` 并排放在一起。**如果我自己都分不清哪个能点，设计就得改。**

> **2026-09-20 修正注记**：本节风险已由 D14 改档**自动消除**。`.done` 最终取**实心绿底**而非浅绿底，与 Badge 的浅绿胶囊形成"体量 + 色彩深浅"双重区分。上文"若做成浅绿底 + 绿字 + 小胶囊"的假设前提不再成立，并列验收保留为回归项。见技术方案 §4.7 修正记录。

### 10.5 新 role 的三项配套决策

**D11 命名候选：**

| 候选 | 评价 |
| --- | --- |
| `.done` | ✅ **推荐**。短、场景词、不与 tone 的 `.success` 撞名 |
