# EasyDesignSystem 支持多平台技术方案和开发计划

> 日期：2026-09-05  
> 状态：方案评审中，尚未开始实施  
> 项目路径：`/Users/yangxuehui/Documents/dev_open_source/EasyDesignSystem`  
> 目标平台：iOS、iPadOS、macOS、Mac Catalyst  
> 暂不支持：visionOS、tvOS、watchOS

## 1. 项目愿景

EasyDesignSystem 的目标不是让四个平台显示完全相同的像素，而是让开发者使用同一套 API 和同一套设计语义，方便、快速地构建具有一致品牌、清晰层级、原生交互和良好可访问性的用户界面。

理想的开发体验是：

```swift
import EasyDesignSystem

struct SettingsView: View {
    var body: some View {
        EDSPage("设置", subtitle: "管理应用偏好") {
            EDSPageSection("通用") {
                EDSGroup {
                    EDSSettingRow("自动更新") {
                        EDSToggle(isOn: $isEnabled, label: "启用")
                    }
                }
            }

            EDSButton("保存", role: .primary) {
                save()
            }
        }
    }
}
```

同一份业务代码应当能够在 iPhone、iPad、原生 macOS 和 Mac Catalyst 上编译运行。设计系统自动完成平台适配，普通调用方不需要编写：

```swift
#if os(macOS)
// macOS 样式
#else
// iOS 样式
#endif
```

## 2. 核心原则

### 2.1 API 统一

- 对外只提供一个主要产品：`EasyDesignSystem`。
- 同一个组件在四个平台保持相同名称、初始化方式和语义。
- 平台差异由设计系统内部解析，业务代码默认不感知平台。
- 只有确实不存在跨平台等价物的能力，才提供受平台限制的附加 API。
- 不为 iOS、macOS 分别建立 `EDSButtonIOS`、`EDSButtonMac` 之类的平行组件。

### 2.2 兼容现有 API

现有 API 兼容优先级：

1. 源码兼容：现有调用代码应尽量无需修改即可重新编译。
2. JSON 兼容：现有主题 JSON 应继续加载，新增字段缺失时使用合理默认值。
3. 语义兼容：`.primary`、`.card` 等既有含义不能改变。
4. 视觉兼容：macOS 现有页面不应出现无意的大面积视觉变化。
5. 二进制兼容：当前阶段不作为硬性目标，但发布稳定版后需要纳入版本策略。

实现方式：

- 不删除或重命名现有公开类型、枚举 case、属性和初始化方法。
- 新能力优先通过有默认值的新参数、新重载或新 Token 增量提供。
- 现有 macOS 专属初始化方法在 macOS 上继续保留。
- 需要废弃的 API 先标记 `@available(*, deprecated, ...)`，至少跨一个版本迁移，不直接删除。
- 建立 API 基线清单和兼容编译样例，持续检测破坏性变化。

### 2.3 体验一致

“体验一致”包括：

- 品牌色、语义色、字体层级、间距尺度和圆角语言一致。
- 相同状态使用相同语义：主要、次要、成功、警告、危险、禁用、加载。
- 相同组件承担相同职责。
- 浅色和深色模式都清晰可读。
- VoiceOver、Dynamic Type、键盘、鼠标、触控等输入方式均可用。

“体验一致”不意味着：

- 所有平台强制相同控件高度。
- iPhone 页面强制使用 macOS 的宽页面边距。
- macOS 为了模仿触屏而放弃鼠标悬停和键盘操作。
- iPad 和 iPhone 无论宽度都使用相同排版。

## 3. 平台支持基线

### 3.1 推荐最低版本

| 平台 | 最低版本 | 说明 |
| --- | --- | --- |
| iOS | iOS 17 | 覆盖 iPhone |
| iPadOS | iPadOS 17 | SwiftPM 随 iOS 平台声明，单独验证界面 |
| macOS | macOS 14 | 保持现有最低版本 |
| Mac Catalyst | Mac Catalyst 17 | 随 iOS 平台声明，单独构建验证 |

`Package.swift` 中只需声明：

```swift
platforms: [
    .iOS(.v17),
    .macOS(.v14)
]
```

Swift Package Manager 没有单独的 iPadOS 和 Mac Catalyst 平台声明；它们需要通过 iPad 模拟器和 Catalyst 构建目标完成验证。

### 3.2 暂不纳入

- visionOS
- tvOS
- watchOS

代码设计应避免故意阻断未来扩展，但本轮不为上述平台增加条件分支、示例和测试，也不宣称支持。

## 4. 当前项目审计

### 4.1 当前结构

当前 Package 包含：

- Token：颜色、间距、圆角、字体、控件尺寸、描边、阴影、渐变。
- 主题：全局主题、局部 Environment 主题、JSON 导入导出、预设主题。
- Easy API：Page、Content、Section、Group、Card、Plain。
- 精细组件：按钮、徽章、开关、设置行、状态页、Pill、Hero、折叠区等。
- Catalog：精细 API、Easy API 和 Token 编辑器。
- 测试：公开入口编译、颜色解析、JSON 默认值、主题环境和 Easy Recipe。

整体架构可以延续，不需要推翻重写。

### 4.2 已识别的平台耦合

| 位置 | 当前问题 | 影响 |
| --- | --- | --- |
| `Package.swift` | 只声明 macOS 14 | iOS App 不能将其视为正式支持依赖 |
| `EDSDesignTokens.swift` | `toHex()` 只有 AppKit 实现，其他平台返回 `#000000` | iOS 导出主题可能静默写成黑色 |
| `EDSSurfaces.swift` | 公共组件直接存储并公开 `NSImage` | iOS 无法编译统一模块 |
| `EDSSurfaces.swift` | 使用 `Image(nsImage:)` | AppKit 专属 |
| `EDSCollapsibleSection` | 直接使用 macOS 的 `.controlBackgroundColor` | UIKit 平台可能无法编译或语义不一致 |
| `EDSDesignSystemPreview.swift` | 使用 `NSColorWell`、`NSViewRepresentable` | Catalog 只能在 macOS 使用 |
| Button Style | 默认按钮高度 34pt | 不满足 iOS 常规触控目标 |
| `EDSPage` / Easy Page | 默认 32pt 页面 padding、880pt 最大宽度 | iPhone 紧凑宽度不够自适应 |
| Button / Pill | 交互反馈依赖 `onHover` | 触屏设备没有悬停状态 |
| Pill 删除按钮 | 只有悬停时可见并可点击 | iPhone/iPad 上删除入口不可用 |
| Typography | 大量使用固定字号 | Dynamic Type 支持不足 |
| 多个组件 | 存在固定高度、固定图标尺寸和限制行数 | 大字体下可能截断 |
| Catalog | 只有 Swift Package Preview，没有完整多平台宿主 App | 无法可靠执行 iOS/Catalyst UI 集成验证 |

### 4.3 当前验证情况

- 当前 Git 工作区在创建本文档前是干净的。
- 已确认当前工具链为 Swift 6.3.3。
- 现有单元测试内容已核对。
- 本次调研中的 `swift test` 受到执行环境对 SwiftPM 内部 sandbox/module cache 的限制，未形成有效的基线测试结论。
- 正式开发第一项必须在允许 SwiftPM 正常运行的环境重新执行 macOS 基线构建和测试。

## 5. 目标架构

### 5.1 保持单一公共模块

推荐继续保留：

```text
EasyDesignSystem
├── Tokens
├── Theme
├── Adaptation
├── Rendering
├── Components
└── Resources
```

对外仍然只需要：

```swift
import EasyDesignSystem
```

不建议把公共产品拆成 `EasyDesignSystemIOS` 和 `EasyDesignSystemMacOS`。如果内部将来为了编译速度拆 Target，也不能要求业务 App 根据平台选择不同产品。

### 5.2 内部平台适配层

增加内部适配层，集中处理：

- AppKit 和 UIKit 颜色桥接。
- 平台默认背景和分隔线。
- 触控、鼠标及混合输入的最小交互尺寸。
- 紧凑与常规宽度下的页面 padding 和最大宽度。
- Hover 是否参与视觉状态。
- Dynamic Type 和辅助功能设置。
- Reduce Motion 下的动画策略。

业务组件只读取已经解析后的语义值，不直接判断 `os(macOS)`。

推荐内部结构：

```text
Sources/EasyDesignSystem/
├── Core/
│   ├── EDSPlatformCapabilities.swift
│   ├── EDSResolvedMetrics.swift
│   └── EDSAdaptiveEnvironment.swift
├── Platform/
│   ├── EDSPlatformColor+AppKit.swift
│   └── EDSPlatformColor+UIKit.swift
└── Components/
```

文件结构可以渐进调整；不以移动文件作为项目目标。

### 5.3 自适应输入

组件最终样式由以下输入共同决定：

```text
品牌 Token
    +
平台能力（AppKit / UIKit / Catalyst）
    +
环境（Size Class、Dynamic Type、Reduce Motion）
    +
组件语义（primary、card、danger 等）
    =
最终渲染样式
```

调用方继续使用现有 API，不需要传入“当前是 iPhone”。

### 5.4 平台档案

内部可建立三种默认档案：

| 档案 | 默认使用场景 | 特征 |
| --- | --- | --- |
| Touch | iPhone、iPad | 触控目标至少 44pt，紧凑页面边距 |
| Pointer | 原生 macOS | 控件较紧凑，支持 hover 和键盘 |
| Hybrid | Mac Catalyst | 保留合理点击面积，同时支持 hover、键盘和窗口缩放 |

平台档案属于内部实现。只有测试、Preview 或特殊宿主需要强制覆盖时，才暴露一个统一的高级覆盖入口；普通页面不应配置。

## 6. Token 演进方案

### 6.1 保留现有 Token

以下公开成员继续保留：

- `EDSColorTokens`
- `EDSSpacingTokens`
- `EDSRadiusTokens`
- `EDSTypographyTokens`
- `EDSControlSizeTokens`
- `EDSStrokeTokens`
- `EDSShadowTokens`
- `EDSHeroGradient`
- `EDSDesignTokens`

现有字段、初始化方法和 JSON Key 不删除、不改名。

### 6.2 增加自适应 Token

建议增量增加：

```swift
public struct EDSAdaptiveLayoutTokens: Codable, Equatable, Sendable {
    public var compactPagePadding: CGFloat
    public var regularPagePadding: CGFloat
    public var readableContentMaxWidth: CGFloat
    public var minimumTouchTarget: CGFloat
    public var minimumHybridTarget: CGFloat
}
```

是否采用这个确切名称可在实施时确定，但需要表达：

- 紧凑页面边距。
- 常规页面边距。
- 可读内容最大宽度。
- 触控最小命中区域。
- 混合输入最小命中区域。

现有 `controlSize.buttonHeight`、`fieldHeight` 和 `rowMinHeight` 继续表达视觉尺寸；最终命中尺寸由适配层保证。这样 macOS 现有 34pt 按钮不必被全局改成 44pt。

### 6.3 JSON 向后兼容

- 新 Token 必须使用 `decodeIfPresent` 和默认值。
- 旧 JSON 不含新字段时应正常加载。
- 新 JSON 应保留现有 Key。
- 未知 Key 继续忽略。
- 增加旧版完整 JSON、旧版部分 JSON、新版 JSON 的回归 Fixture。
- JSON round-trip 后不得将合法颜色变成 `#000000`。

### 6.4 颜色策略

颜色桥接必须明确区分：

```swift
#if canImport(AppKit) && !targetEnvironment(macCatalyst)
import AppKit
#elseif canImport(UIKit)
import UIKit
#endif
```

要求：

- 原生 macOS 使用 `NSColor`。
- iOS、iPadOS、Mac Catalyst 使用 `UIColor`。
- `Color.toHex()` 在四个平台正确转换 sRGB。
- 动态系统颜色导出时使用明确的外观解析规则并写入文档。
- 无法转换时不能静默伪装为正常黑色；如保留非抛出 API，需要有可测试、可诊断的回退策略。
- 页面、卡片、分隔线继续优先使用系统语义色，自动适配深色模式。

### 6.5 字体策略

现有字体属性名称继续保留，但内部实现需要支持 Dynamic Type。

推荐：

- 标题、正文、说明等语义角色映射到系统 Text Style。
- 自定义字号通过相对 Text Style 缩放，而不是永久固定像素。
- 数字和代码仍可保留 monospaced design。
- 不改变调用方式，例如 `theme.typography.body` 继续有效。
- 增加超大辅助字号下的布局测试。

## 7. 公共 API 兼容方案

### 7.1 必须保持可编译的现有入口

至少包含：

- `.easyDesign()`
- `.easyDesign(.card)`
- `.easyDesign(theme:)` 和 `.easyDesign(tokens:)`
- `.easyDesignTheme(...)`
- `EDSTheme.shared.configure`
- JSON 主题加载和导出。
- `EDSPage`、`EDSPageStack`
- `EDSPageSection`、`EDSSection`
- `EDSCard`、`EDSGroup`
- `EDSButton` 和四种 Role。
- `EDSBadge`、`EDSToggle`
- `EDSSettingRow`、`EDSValueRow`、`EDSInlineField`
- 空、错误、加载和进度状态组件。
- `EDSPill`、`EDSPillFlow`
- `EDSHeroPanel`、`EDSCollapsibleSection`
- `EDSComparisonSection`

### 7.2 图像 API

`EDSMultilineSubtitleRow(iconImage: NSImage?)` 当前阻止统一模块在 iOS 编译。

推荐改造：

1. 增加全平台统一入口，接受 SwiftUI `Image` 或 `@ViewBuilder` 图标。
2. 内部统一存储 SwiftUI View，不存储 `NSImage`。
3. 在原生 macOS 条件下保留现有 `NSImage` 初始化重载，并转换为 SwiftUI `Image`。
4. iOS 调用方不需要知道 `NSImage`。
5. 在 macOS 上给旧初始化方法添加迁移提示，但首个多平台版本不移除。

示意：

```swift
EDSMultilineSubtitleRow(
    icon: Image(systemName: "book"),
    title: "标题",
    subtitle: "说明"
) {
    Toggle("", isOn: $enabled)
}
```

### 7.3 平台差异的高级覆盖

默认 API 必须自动工作。若确有特殊页面需要覆盖，建议提供语义化选项，而不是暴露平台分支：

```swift
.easyDesign(
    .page,
    options: EDSEasyOptions(
        padding: .automatic,
        maxContentWidth: .automatic
    )
)
```

现有 `EDSEasyOptions` 不变。必要时可以新增 `.compact`、`.regular` 等语义值，但不新增 `.iPhone` 或 `.macOS` 这种把平台写死在页面里的配置。

### 7.4 API 兼容检测

建立三层保护：

- 编译测试：把 README 和旧版示例中的调用方式写入测试。
- Symbol Graph／API Digester：保存公开 API 基线，在 CI 中检测删除和签名变化。
- 迁移测试：用旧版主题 JSON 和旧版示例 App 构建新版本 Package。

## 8. 组件适配规范

### 8.1 页面和布局

`EDSPage`、`EDSPageStack` 和 `.easyDesign(.page)`：

- 紧凑宽度使用较小页面边距。
- 常规宽度使用现有较宽间距。
- 最大内容宽度继续限制可读行长。
- iPhone 尊重 Safe Area。
- iPad 分屏和 Catalyst 窄窗口自动收缩。
- 不内置 `NavigationStack`，继续由业务 App 决定导航结构。
- 现有显式 `padding`、`maxWidth` 参数优先于自动值。

### 8.2 卡片和分组

- `EDSCard`、`EDSGroup` 的语义保持不变。
- 背景使用各平台系统语义色。
- 深色模式下避免过重阴影。
- 增强对比度环境下提高边界可辨识度。
- 显式传入的背景、圆角和 padding 继续优先。

### 8.3 按钮

- 四种 Role 和现有初始化方法保持不变。
- iOS/iPadOS 的点击区域至少 44×44pt。
- macOS 可保留较紧凑的视觉高度。
- Catalyst 使用混合输入档案。
- Pressed、Hover、Disabled 状态含义统一。
- 只有支持指针时 Hover 才影响表现。
- Reduce Motion 下取消或减弱缩放动画。
- 大字体时使用 `minHeight`，避免固定高度裁切文字。

### 8.4 Pill

- 触屏环境中删除按钮必须始终可发现、可点击。
- 指针环境可以在悬停时增强删除按钮，但不能把悬停作为唯一入口。
- 删除按钮满足触控目标，同时不破坏 Pill 的紧凑视觉尺寸。
- 支持 VoiceOver 的标签、删除动作和选中状态。
- 流式布局在窄屏和大字体下正确换行。

### 8.5 设置行和表单

- 行的视觉高度和实际命中高度分离。
- iPhone 上标题与 Trailing 内容空间不足时允许合理换行或转为纵向布局。
- Toggle 不使用空白或重复的 VoiceOver 标签。
- TextField、Picker 等由系统提供输入行为，EDS 只管理外围层级和间距。
- Catalyst 和 macOS 支持键盘焦点顺序。

### 8.6 Sidebar

- 侧边栏图标和菜单项保持 API 统一。
- iPad 和 Mac 使用 `NavigationSplitView` 时保持良好表现。
- iPhone 折叠为单栏导航时组件不假设左侧栏永久存在。
- 设计系统提供行和选中态，不接管 App 的 NavigationPath。

### 8.7 状态组件

- 空状态、错误、加载和进度状态在四个平台共享 API。
- iPhone 上避免不必要的大面积空白。
- 加载状态提供可访问性提示。
- 进度值统一限制在合法范围。
- 状态不能只依赖颜色表达。

### 8.8 折叠与动画

- `EDSCollapsibleSection` 改用语义卡片背景。
- 保留现有初始化方法和展开行为。
- 支持 VoiceOver 展开／折叠状态。
- 支持键盘触发。
- Reduce Motion 下使用弱化过渡。

## 9. 主题系统方案

### 9.1 保留现有配置入口

继续支持：

```swift
EDSTheme.shared.configure { tokens in
    tokens.colors.primary = .blue
}
```

以及：

- `applyPreset`
- `configure(jsonData:)`
- `configure(jsonFileURL:)`
- `configure(jsonResource:bundle:)`
- `applyDefaultThemeFromPackage()`
- `exportJSON()`
- `exportJSONString()`

### 9.2 全局与局部主题

- 全局主题继续适合 App 启动时一次配置。
- Environment 局部主题继续用于 Preview、独立功能区和多品牌场景。
- 本轮不强制把 `EDSTheme.shared` 改为运行时响应式主题。
- 如果以后支持实时换肤，应单独设计并保持当前调用兼容。

### 9.3 Sendable 和并发

`EDSTheme` 当前使用 `@unchecked Sendable`，同时公开可变 Token。多平台改造期间需要专项审计：

- 明确所有写入发生在 MainActor。
- 避免后台线程读写竞争。
- 不为了消除警告而扩大 `@unchecked Sendable`。
- 如果调整内部存储，不改变现有配置 API。

## 10. 多平台 Catalog 与示例

### 10.1 建立真实宿主 App

现有 Catalog library 和 Preview 可以保留，但不足以验证四个平台。

建议新增一个最小的 Multiplatform Catalog App：

```text
Examples/PlatformCatalog/
├── Shared/
├── iOS/
├── macOS/
└── PlatformCatalog.xcodeproj
```

共享页面展示所有公共组件；平台目录只放 App 入口或不可避免的系统集成代码。

这个宿主工程用于：

- iPhone 模拟器构建和截图。
- iPad 模拟器构建和分屏检查。
- 原生 macOS 构建。
- Mac Catalyst 构建和窗口缩放检查。
- UI 测试和 Accessibility Identifier 验证。

### 10.2 Token 编辑器

当前 Token 编辑器使用 `NSColorWell`。

推荐：

- 保留 macOS 的 `NSColorWell` 实现。
- iOS/iPadOS 使用 SwiftUI `ColorPicker`。
- 对外表现和 Token 编辑结果一致。
- 平台实现放在 Catalog 内部，不进入业务组件公共 API。
- 文件导出在各平台使用系统支持的 Document/File Exporter。

- iPhone 紧凑宽度。

## 15. 风险与应对

### 15.1 为统一 API 牺牲平台体验

风险：为了让代码一样，所有平台被迫使用同一尺寸和交互。

应对：统一的是语义和调用方式，渲染通过 Touch、Pointer、Hybrid 档案自适应。

### 15.2 破坏现有 macOS 项目

风险：修改默认 padding、按钮高度或公共初始化方式后，旧页面发生变化。

应对：保留 API、显式配置优先，并使用旧 Catalog 截图、旧调用编译样例和 API Baseline 回归。

### 15.3 Token JSON 不兼容

风险：新增字段导致旧主题无法加载，或 iOS 颜色导出错误。

应对：所有新增字段带默认值；建立旧、新 Fixture 和跨平台 round-trip 测试。

### 15.4 条件编译散落

风险：每个组件自行判断平台，长期维护成本持续上升。

应对：平台代码集中在内部 Platform/Adaptation 层，普通组件只使用语义值。

### 15.5 Catalyst 被误当作 macOS

风险：`canImport(AppKit)`、`os(macOS)` 或外观判断选错实现。

应对：明确使用 `targetEnvironment(macCatalyst)`，并把 Catalyst 作为独立构建和人工验证目标。

### 15.6 只有编译测试，没有真实体验

风险：库能编译，但触屏入口、分屏、大字体或键盘无法使用。

应对：建立真实 Multiplatform Catalog App，把布局、交互和可访问性纳入验收。

### 15.7 范围膨胀

风险：多平台项目演变成重写所有组件或顺带支持更多平台。

应对：本轮只支持四个平台；保持现有组件集合，以兼容和适配为主，不同时增加大量新业务组件。

## 16. 验收标准

EasyDesignSystem 多平台支持完成时必须满足：

- 同一个 `EasyDesignSystem` 产品支持 iOS 17、iPadOS 17、macOS 14 和 Mac Catalyst 17。
- 常规页面不需要平台条件编译。
- 当前公开 API 尽量保持源码兼容，并有自动化兼容检查。
- 旧版主题 JSON 可以直接加载。
- 四个平台颜色加载和导出正确，不出现静默黑色。
- Page、Card、Group、Button、Row、Toggle、Pill 和状态组件在四个平台可用。
- iPhone/iPadOS 触控目标满足要求。
- macOS/Catalyst 的 Hover、键盘和窗口缩放可用。
- Dynamic Type、VoiceOver、Reduce Motion 和深色模式通过验证。
- 多平台 Catalog 能够展示和验证完整组件集合。
- README、迁移指南和发布说明完整。
- 有一个可供业务 App 固定依赖的版本或提交。
- 功课助手完成最小集成验证后，才进入其界面优化开发。
