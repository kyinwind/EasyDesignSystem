## 二、根因（两个独立问题，都在主题预览栏里）

`EDSThemeBar` 是 0.3.0 新增的、对所有 tab 生效的顶部主题选择栏。它给"适配"页
（`--adaptive-preview`，也就是无障碍审计跑的那一页）引入了两个失败项。

### 问题 A：固定字号字体 → `Dynamic Type font sizes are unsupported`

```swift
Text("预览主题").font(EDSTheme.shared.typography.captionStrong)   // = .system(size: 12, …)
Text(entry.detail).font(EDSTheme.shared.typography.monoCaption)   // = .system(size: 11, …)
```

`EDSTypographyTokens.caption*` / `monoCaption` 返回 **`.system(size:)` 固定字号**，不参与
Dynamic Type 缩放。包内其它组件一律走 `edsFont(...)`，它映射到 `.caption` / `.caption2`
这类**语义文本样式**（见 `EDSScaledTypography.swift`），所以能过审计。

### 问题 B：`ViewThatFits` → `Dynamic Type font sizes are partially unsupported`

第一个修复版本把栏内容包进 `ViewThatFits(in: .horizontal)`（三级降级：完整 / 去详情 / 去色块），
结果**栏内每一个 Text 都被判 partially unsupported**，包括完全不加字号修饰的裸 `Text("PA")`。

对照实验（逐次跑审计，只看问题条数）：

| 栏内容 | 问题数 |
|---|---|
| `HStack` + `ViewThatFits` + 4 个探针 Text | 5（探针 4 条 + 标题 1 条，一一对应） |
| 去掉 `ViewThatFits`，留 3 个探针 Text（裸 `Text` / `.font(.body)` / `.edsFont(.bodyStrong)`） | **0** |
| 换成普通 `VStack`（主行 + 详情行） | 2 —— 只剩详情行 |
| 最终版：普通 `HStack`、不显示详情行 | **0** |

⇒ 断定：**`ViewThatFits` 是触发条件**。与字体无关——换语义字号、去掉 `.fixedSize()` 都无效；
   裸 `Text` 也会中招，说明不是"某个字体不被支持"，而是**审计在 `ViewThatFits`
   度量期采样文本、误判为"部分不支持"**。

### 为什么 iPad 不失败

`EDSPlatformCatalogUITests` 按窗口宽度分组审计项：

```swift
let isPad = app.windows.firstMatch.frame.width >= 700
let auditTypes = isPad
    ? [.textClipped, .hitRegion, .sufficientElementDescription, .trait]
    : [.dynamicType, .textClipped, .hitRegion, .sufficientElementDescription, .trait]
```

**iPad 组不含 `.dynamicType`** ⇒ 问题 A / B 在 iPad 上根本不被检查。
这正好解释了"iPhone 必挂、iPad 通过"。

### 附带修掉的第三条：`Text clipped`

详情行 `entry.detail`（`monoCaption` + `lineLimit(1)`）无论独占一行与否，
稳定被判 `Text clipped`。**已把该行从主题栏移除**——主题名 Picker 与五色色块
已经足够表达当前主题，少一行还换回更紧凑的高度。

### 为什么测试要打印元素

失败时 CI 日志原本只有一句：

```
Failing tests:
	EDSPlatformCatalogUITests.testAdaptiveCatalogPassesSystemAccessibilityAudit()
```

加了 handler 之后变成：

```
EDS_A11Y_AUDIT_ISSUE | description=Dynamic Type font sizes are partially unsupported
                     | element=StaticText {{16.0, 81.0}, {49.3, 14.3}}, label: '预览主题'
```

本次排查如果没有它，会在"到底哪个元素出问题"上多绕好几轮。

```bash
cd Examples/PlatformCatalog
xcodebuild -project EDSPlatformCatalog.xcodeproj -scheme EDSPlatformCatalog \
  -destination 'platform=iOS Simulator,id=<iPhone UDID>' \
  -derivedDataPath /tmp/eds-dd -clonedSourcePackagesDirPath /tmp/eds-csp \
  CODE_SIGNING_ALLOWED=NO \
  -only-testing:EDSPlatformCatalogUITests/EDSPlatformCatalogUITests/testAdaptiveCatalogPassesSystemAccessibilityAudit \
  test
```

> ⚠️ `-only-testing` 必须是**三段式** `测试目标/测试类/测试方法`。写成两段式
> （漏掉类名）xcodebuild **不报错，只执行 0 个测试并返回 0**，会拿到一个假的"通过"。
> 本次排查第一轮就被这个坑骗过一次。

## 五、API 兼容性 job：根因假设与对策

`compatibility` job 本地（Xcode 27 / Swift 6.4）通过、CI（Xcode 16.4 / Swift 6.1）失败，
而 GitHub 的 job 日志接口需 admin 权限（403），check-run annotations 只给一句 `exit code 1`。
在拿不到 CI 输出的前提下，从脚本与符号图本身找到了一个**可解释的跨版本假阳性源**。

基线里有 11 条形如下的符号：

```
s:7SwiftUI4ViewP16EasyDesignSystemE04easyE0_5theme7options…   func easyDesign(…)
s:7SwiftUI5ColorV16EasyDesignSystemE5toHexSSyF               func toHex() -> String
```

它们是「本模块对 SwiftUI 类型所做的扩展」的成员，标识符**首段是被扩展类型所属的外部模块**
（`s:7SwiftUI`）。Xcode 16.4 → 27 之间 Apple 把 SwiftUI 拆分为 SwiftUI + SwiftUICore，
同一批扩展的 mangled 前缀随之可能改变——业务代码一字未改，也会被判成"公开 API 被删"。

本地已观察到拆分确实发生：扩展图文件名由 `EasyDesignSystem@SwiftUI.symbols.json` 变成了
`EasyDesignSystem@SwiftUICore.symbols.json`。

### 对策

1. 对非本模块符号做前缀归一化：`s:<长度><外部模块名>` → `s:EXTERNAL_`，其余部分
   （成员名与签名 mangling）仍严格比对。因此真实删除不会被掩盖。
2. 基线缺失或符号图未生成时明确报根因、附 symbolgraph 清单。旧脚本在这种情况下会把
   **整份基线**误报成"已删除"，刷一屏无效信息把真正的原因埋掉。
3. 比对结果按 core / external 分段打印，失败时只列前 50 条，避免日志被刷屏。

### 仍未解决

- [ ] 归一化是否足以让 CI 通过，需下次 push 后确认。**本机无法验证**：只有 Xcode 27，
  装不出 16.4 那套工具链。
- [ ] 若 CI 仍失败，请把 `Check public API baseline` 这一步的输出贴出来。脚本现在会打印
  「core / external 各多少条」「哪几条被移除」「symbolgraph 清单」，足以一次定位。
- [ ] iPad 那次历史偶发失败仍未定位（8 次运行中出现 1 次）。
