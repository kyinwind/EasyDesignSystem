## 一、需求

杨哥原话：

> 三个文件都可以预览包内组件，但是缺少 `EDSTheme.shared.applyPreset()`。我想在预览状态下，有个地方可以选不同颜色风格，选完之后，组件自动变化，我就可以知道这个颜色风格大概是什么感觉了。

拆成两条可验收标准：

1. **预览态下有一处统一的主题选择器**（不是每个示例各自一套）
2. **切换后已渲染的组件立刻变色**——不是"下次打开才生效"

目的：为后续按钮设计讨论提供**可感知**的判断依据（看一眼蓝/橙/紫各是什么调性），而不是靠文字描述。

### 非目标（明确不做）

- ❌ 不改 `Sources/` 下任何包内代码（`EDSTheme`、`EDSButtons` 等一行不动）
- ❌ 不实现风格轴（`EDSButtonStyleProfile`，已决议暂缓）
- ❌ 不做"预设 × 深色外观"矩阵
- ❌ 不改 `EDSDesignSystemPreview` 现有的 draft 编辑器工作流

## 二、三个必须先讲清的硬约束

### 约束 1：`.easyDesignTheme()` 这条路走不通

EDS 有两套读 token 的路径：

| 路径 | 机制 | 能否被 `.easyDesignTheme()` 改变 |
| --- | --- | --- |
| `@Environment(\.edsTheme)` | SwiftUI 环境注入 | ✅ 能 |
| `EDSTheme.shared.xxx` | **直读全局单例** | ❌ **不能** |

而两个 Gallery 文件里大量代码走的是第二条：

| 文件 | `EDSTheme.shared.` 直读次数 | 主要路径 |
| --- | --- | --- |
| `EDSDesignSystemGallery.swift` | **26** | 单例（如 `:40/51/53`、`:341-357`） |
| `EDSDesignSystemPreview.swift` | **15** | 混合（`:187/265/267` 用单例，其余用 draft） |
| `EDSEasyAPIDesignSystemGallery.swift` | **0** | 全走 `easyDesign`（环境） |

**结论：只能改单例（走 `applyPreset`），不能用环境注入。** 反过来说，光改单例也不够——见约束 2。

### 约束 2：`applyPreset` 改了单例，但 SwiftUI 不会重绘

`EDSTheme` 是普通 `final class`，**不是 `ObservableObject`**，也没有 `@Observable`。它没有发出任何变更通知。`EDSTheme.swift:45` 的文档注释原文：

> 建议在 App 启动阶段完成配置，**运行时动态切换主题暂不承诺自动刷新 UI**。

实际后果：`applyPreset(.orange)` 之后，**已经渲染出来的视图不会自己重绘**。用户看到的是"点了没反应"。

### 约束 3：变更顺序有陷阱

天真写法 `onChange(of: selection) { applyPreset(...) }` 的执行顺序是：

```
state 变化 → body 重算（此时单例仍是旧值 ❌）→ onChange 触发（改单例，但不会再次渲染）
```

结果：**永远慢一拍**。必须**先改单例，再改驱动重建的 state**。

## 三、方案：`applyPreset` + `.id()` 强制重建

两个机制配合，缺一不可：

```swift
// ① 先改单例（顺序必须在改 state 之前）
EDSTheme.shared.applyPreset(entry.preset)

// ② 再改 state，通过 .id() 强制销毁并重建子树
contentView.id(appliedRevision)
```

- ① 让所有 `EDSTheme.shared.xxx` 读到新值
- ② 因为 `EDSTheme` 不会通知，所以**由 `.id()` 变化触发 SwiftUI 主动重建**，重建时重新求值全部 token

`.id()` 是 SwiftUI 官方机制：id 变化 = 视为不同视图 = 销毁旧的、创建新的。这是 100% 可靠的刷新手段，代价是子树状态被重置（见 §六 风险）。

### 组件形态

在 `Examples/Catalog/` 新增一个文件，属于已有的 `EasyDesignSystemCatalog` target（`Package.swift:33-37`，path `Examples/Catalog`），**public 导出**供 `PlatformCatalog` 工程复用：

```swift
@MainActor
public struct EDSThemePlayground<Content: View>: View {
    @State private var selectedID: String
    @State private var appliedRevision: Int = 0
    private let content: () -> Content

    public init(initialThemeID: String = ..., @ViewBuilder content: @escaping () -> Content)

    public var body: some View {
        VStack(spacing: 0) {
            EDSThemeBar(selection: selectionBinding)   // 顶部选择器
            Divider()
            content().id(appliedRevision)              // 重建锚点
        }
    }

    /// 顺序即正确性：先 applyPreset，再 bump revision
    private var selectionBinding: Binding<String> {
        Binding(
            get: { selectedID },
            set: { newValue in
                apply(newValue)          // ① 单例
                appliedRevision += 1     // ② 触发重建
            }
        )
    }
}
```

`apply(_:)` 内部调 `EDSTheme.shared.applyPreset(_:)`。并发处理：`View` 协议在 Swift 6 下是 `@MainActor` 隔离的，`Binding.set` 由 SwiftUI 在主线程调用，因此 `apply` 标为 `@MainActor` 即可，无需 `assumeIsolated` hack。

## 四、候选主题清单（帮杨哥"找感觉"）

`EDSPresetTheme` 的 `init(id:name:tokens:)` 是 **public**（`EDSTheme.swift:210`），所以 Examples 层可以现场构造主题，**不必改包**。这正好把"包外 App 换主色"的真实写法演示一遍。

**A 组 · 包内内置预设**（直接引用，验证现状）

| 显示名 | 来源 | primary |
| --- | --- | --- |
| 默认蓝 | `EDSPresetTheme.default` | `#3185FF` |
| 橙 | `EDSPresetTheme.orange` | `#FF6B00` |
| 紫 | `EDSPresetTheme.purple` | `#8B5CF6` |

**B 组 · 包外自定义示例**（Examples 层构造，演示 App 侧换色写法）

| 显示名 | primary | 定位 |
| --- | --- | --- |
| 商务深蓝 | `#1D4ED8` | 对应 RightClickMate / TTSMate 的"偏商务正式" |

顶部栏右侧显示当前主题的 5 色色块，一眼看出语义色是否协调。

### 新增文件的结构

```
EDSCatalogThemePlayground.swift
├── EDSCatalogThemeEntry        // 一个可切换主题（id / name / detail / isBuiltIn / preset + swatchColors）
├── EDSCatalogThemeCatalog      // 候选清单：builtIn(3) + custom(4)、默认 ID、按 id 查找、makeCustom 构造器
├── EDSThemeBar                 // 顶部栏：Picker(分组) + 5 色色块 + 当前条目说明
└── EDSThemePlayground<Content> // 外壳：VStack { Bar; Divider; content().id(appliedRevision) }
```

`EDSThemePlayground` 的核心 8 行（顺序即正确性）：

```swift
Binding(
    get: { selectedID },
    set: { newValue in
        MainActor.assumeIsolated {
            applyTheme(withID: newValue)   // ① 先落全局单例
            selectedID = newValue          // ② 再改 state
            appliedRevision += 1           // ③ 触发 `.id` 变化 → 重建子树
        }
    }
)
```

`MainActor.assumeIsolated` 用于在 `Binding.set`（nonisolated 闭包）里安全调用 `@MainActor` 的 `applyPreset`。Picker 交互必然发生在主线程，运行时断言成立，Swift 6 严格并发下零警告通过编译。

## 六、影响面与风险

| # | 风险 | 评估 | 处置 |
| --- | --- | --- | --- |
| R1 | **子树状态被重置**。`.id()` 重建会让 Gallery 的侧边栏选中项、Preview 的 draft 编辑器回到初始值 | 中 | 接受。切主题语义上就是"换一套视觉重看"，重置可预期。且 draft 会重新读取新主题值，行为合理 |
| R2 | **UITests 受影响**。`Examples/PlatformCatalog/UITests/` 有 9 个用例 | 低 | 已逐个核对：全部通过 `--adaptive-preview` 启动，落在 tab 3（适配），**不断言任何颜色**，断言的是文本 `跨平台适配`、`继续`/`取消` 按钮、`adaptive.profile` 等控件。顶部栏不引入 `switch`/`checkbox`，不会改变 `app.switches.firstMatch` 指向 |
| R3 | **无障碍审计**。`testAdaptiveCatalogPassesSystemAccessibilityAudit` 会跑 `.hitRegion` / `.elementDetection` | 低 | 选择器用系统原生 `Picker`，带 `Text` label 与 `accessibilityIdentifier("catalog.theme.picker")`，点击区域由系统保证 |
| R4 | **实时性能**。重建整个 Gallery（数百个视图） | 低-中 | 仅在切换瞬间发生一次；若实测卡顿，退路是给 `content()` 加 `.drawingGroup()` 或把 `.id()` 下移一层。**实测为准** |
| R5 | **深浅外观不涉及**。颜色是 hex 静态 sRGB，不随 `colorScheme` 变 | 说明 | 本方案不处理，与需求无关。若杨哥想同时看深色，另开一轮 |
| R6 | 顶部栏挤压 `--narrow-window`（620px）布局 | 低 | 顶部栏为单行 ~44pt，615px 宽度足够放 Picker + 色块；必要时色块可省略 |
