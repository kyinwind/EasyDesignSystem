## 一、目标与范围

### 1.1 一句话目标

把 `EDSButton` 从"一维枚举"改造为"**三维正交原语 + 一维预设别名表**"的双入口结构，**一份样式实现**替换现有四份复制，并新增 `.done` 预设。

### 1.2 硬约束（不可违反）

| # | 约束 | 含义 |
| --- | --- | --- |
| C1 | **源码零破坏** | 现有 App、README 示例、Examples、Tests 不改一行即可编译通过 |
| C2 | **视觉零变化（仅一处例外）** | 现有 4 种按钮的像素表现完全不变；唯一例外是 D16（见 §七） |
| C3 | **不改共享基建** | `EDSResolvedMetrics`（7 个文件在用）、`EDSDesignTokens` 的 Codable 结构不动 |
| C4 | **不加 JSON 字段** | 新增颜色一律用**计算属性**派生，`EDSDefaultTheme.json` 不动 |

### 1.3 明确不做（记录在案）

loading 态、icon-only（`EDSIconButton`）、两套一维 API、风格轴、自定义 focus 视觉、`onPrimary` token（`.white` 硬编码保留）。

## 二、类型设计

### 2.1 三个正交维度（新增）

嵌套在 `EDSButton` 下，与既有 `EDSButton.Role` 保持同一命名空间惯例。

```swift
public struct EDSButton: View {

    // 三个正交维度
    public enum Emphasis: String, Sendable, Hashable, CaseIterable {
        case filled   // 实心：最强视觉
        case outline  // 描边：次强
        case soft     // 浅色底：弱
        case plain    // 纯文字：最弱
    }

    public enum Tone: String, Sendable, Hashable, CaseIterable {
        case accent   // 主题色（正常操作）
        case neutral  // 中性灰
        case danger   // 破坏性
        case success  // 成功 / 已完成
        case warning  // 警告
    }

    public enum Size: String, Sendable, Hashable, CaseIterable {
        case small    // 28
        case regular  // 34（= 现有 buttonHeight）
        case large    // 44
    }
}
```

**为什么嵌套而不做成顶层 `EDSEmphasis`**：避免污染调用方的全局命名空间（尤其 `Size` 是极常见的词）。嵌套后仍可被包外引用（`EDSButton.Tone.danger`），App 自封装不受影响。

**为什么加 `CaseIterable`**：纯新增合成属性，不破坏兼容；让 Examples 能遍历展示全部组合（本方案的验收手段之一）。

### 2.2 `Role` 降级为「预设别名表」

```swift
public enum Role: String, Sendable, Hashable, CaseIterable {
    case primary    // 保留
    case secondary  // 保留
    case soft       // 保留
    case danger     // 保留
    case done       // 新增（D11）
}
```

**定位说明（关键概念）**：`Role` **不再是"一个维度"**，而是一张"快捷方式对照表"。它内部的条目允许混用视觉词（`.primary`）与场景词（`.done`），因为别名表本来就不要求内部同构——类比 Bootstrap 的 `.btn-primary` / `.btn-danger`。

映射表：

| `Role` | → emphasis | tone | size | 说明 |
| --- | --- | --- | --- | --- |
| `.primary` | `.filled` | `.accent` | `.regular` | 与现有 `EDSPrimaryButtonStyle` 逐像素一致 |
| `.secondary` | `.outline` | `.accent` | `.regular` | 与现有 `EDSSecondaryButtonStyle` 逐像素一致 |
| `.soft` | `.soft` | `.accent` | `.regular` | 与现有 `EDSSoftButtonStyle` 逐像素一致 |
| `.danger` | `.filled` | `.danger` | `.regular` | 与现有 `EDSDangerButtonStyle` 逐像素一致 |
| `.done` | `.filled` | `.success` | `.regular` | **新增**：实心绿底 + 近黑字 + ✓（D14 目视后由 `.soft` 改档，见 §4.7） |

> **别名表膨胀约束**：新增 `Role` 必须对应"真实且重复出现的场景"，而非"这个组合我没试过"。建议上限 8–10 条；超过则说明该直接使用三维入口。

### 2.3 外观值对象与解析器

**对外暴露的值对象**（public，供 App 自封装与调试）：

```swift
public struct EDSButtonAppearance: Sendable, Hashable {
    public var emphasis: EDSButton.Emphasis
    public var tone: EDSButton.Tone
    public var size: EDSButton.Size

    public init(
        emphasis: EDSButton.Emphasis = .filled,
        tone: EDSButton.Tone = .accent,
        size: EDSButton.Size = .regular
    )
}
```

**内部解析结果**（`internal`，不对外）：

```swift
struct EDSResolvedButtonVisual {
    let foreground: Color
    let background: Color?      // filled / soft 有值；outline / plain 为 nil
    let borderColor: Color?     // 仅 outline 有值
    let borderWidth: CGFloat    // 仅 outline 有意义
    let height: CGFloat         // 视觉高度（未与最小可点区域合并）
    let horizontalPadding: CGFloat
}
```

**解析入口**（纯函数，无状态，便于单测）：

```swift
extension EDSButtonAppearance {
    func resolved(tokens: EDSDesignTokens) -> EDSResolvedButtonVisual
}
```

设计要点：
- **只依赖 `tokens`**，不读 `EDSTheme.shared` 单例 → 纯函数、可测、不依赖全局状态
- **不需要 `profile` / `horizontalSizeClass`**：解析器只算"视觉高度"（如 34），
  与最小触控面积的合并由渲染层调用 `metrics.interactiveHeight(for:)` 完成
  （`EDSResolvedMetrics` 被 7 个文件共享，职责边界不动）
- 不持有任何 `@State` / `@Environment`

> **实现约束（踩过）**：`@Environment` / `@State` 只有定义在 `View` 上才会被 SwiftUI 注入。
> 因此全部视觉逻辑落在 `EDSButtonVisualBody`（一个 `View`）上，各 `ButtonStyle`
> 只负责把 `ButtonStyleConfiguration` 传进来。**不能**让旧样式在 `makeBody` 里直接调用
> 另一个 `ButtonStyle.makeBody` —— 那样环境值不会生效。

## 三、API 设计

### 3.1 三个 init 并存

```swift
public struct EDSButton: View {

    // ① 旧签名 A —— 原样保留，零改动
    public init(
        _ role: Role = .primary,
        action: @escaping () -> Void,
        @ViewBuilder label: @escaping () -> some View
    )

    // ② 旧签名 B —— 原样保留，零改动
    public init(
        _ title: LocalizedStringKey,
        role: Role = .primary,
        systemImage: String? = nil,
        action: @escaping () -> Void
    )

    // ③ 新签名 C —— 三维入口
    public init(
        _ title: LocalizedStringKey,
        emphasis: Emphasis,            // ← 故意不给默认值
        tone: Tone = .accent,
        size: Size = .regular,
        systemImage: String? = nil,
        action: @escaping () -> Void
    )
}
```

### 3.2 为什么 `emphasis` 不能有默认值（本次最关键的技术细节）

如果给 `emphasis` 默认值 `.filled`，则 `EDSButton("确定") { }` **同时匹配签名 B 和签名 C**，Swift 直接报：

```
error: ambiguous use of 'init(_:emphasis:tone:size:systemImage:action:)'
```

**不给默认值**是消除歧义的唯一手段——签名 C 强制调用方至少写出一个维度，签名 B 因而成为"零维度参数"的唯一归属。三条路径由此各自成立：

```swift
EDSButton("确定", role: .primary) { save() }                        // → 签名 B（预设）
EDSButton("忽略并删除", emphasis: .soft, tone: .danger) { }           // → 签名 C
EDSButton("确定", emphasis: .soft, tone: .danger, size: .small) { }   // → 签名 C
EDSButton("保存", emphasis: .filled) { }                            // → 签名 C（唯一必填维度）
```

### 3.3 为什么不是一个 init 带四个参数

杨哥原始提案是 `EDSButton("确定", emphasis, tone, size, role)`。这个形状在 Swift 里无合法实现，三条路都堵死：

| 尝试 | 结果 |
| --- | --- |
| `role` 给默认值 | 三维与 role **两个真源冲突**（三维说 soft+danger，role 说 filled+accent）。编译不报错，但行为取决于实现内部判定顺序 → **隐性 bug 温床** |
| `role` 默认 `nil` | `EDSButton("确定")` 无样式可渲染，需为"什么都没填"补隐式兜底规则 |
| `role` 放最后给默认值 | 与签名 B **撞车**，编译器报 ambiguous |

### 3.4 `EDSButton.body` 的实现

```swift
public var body: some View {
    Button(action: action) { label() }
        .buttonStyle(EDSButtonStyle(appearance: resolvedAppearance))
}
```

其中 `resolvedAppearance` 由 `role` 走别名表、或由三维参数直接构造：

```swift
private var resolvedAppearance: EDSButtonAppearance {
    if let roleAppearance { return roleAppearance }        // 签名 B 路径
    return EDSButtonAppearance(emphasis: emphasis, tone: tone, size: size)  // 签名 C 路径
}
```

### 3.5 旧的 4 个 ButtonStyle 处置

**全部保留为公开类型，内部改为转发**：

```swift
public struct EDSPrimaryButtonStyle: ButtonStyle {
    public init() {}
    public func makeBody(configuration: Configuration) -> some View {
        EDSButtonStyleCanvas(
            configuration: configuration,
            appearance: .init(emphasis: .filled, tone: .accent, size: .regular)
        )
    }
}
```

`EDSSecondaryButtonStyle` / `EDSSoftButtonStyle` / `EDSDangerButtonStyle` 同理。

**理由**：这 4 个类型是 public，外部 App 可能直接 `.buttonStyle(EDSPrimaryButtonStyle())`。保留即有零破坏保证；转发实现让它们自动获得未来的统一改进。

## 四、三维 → Token 映射表（核心）

### 4.1 前景色（文字色）

| tone ＼ emphasis | `.filled` | `.outline` | `.soft` | `.plain` |
| --- | --- | --- | --- | --- |
| `.accent` | `.white` ⚠️历史 | `colors.primary` | `colors.primary` | `colors.primary` |
| `.neutral` | `colors.pageBackground` | `Color.primary` | `Color.primary` | `Color.primary` |
| `.danger` | `.white` ⚠️历史 | `colors.danger` | `colors.danger` | `colors.danger` |
| `.success` | **`colors.textPrimary`** | `colors.success` | **`colors.textPrimary`** | `colors.success` |
| `.warning` | **`colors.textPrimary`** | `colors.warning` | `colors.warning` | `colors.warning` |

**三条规则说明：**

1. **`.accent` / `.danger` 的实心档保持 `.white`** —— 现有 `.primary` / `.danger` 用的就是它，改成 token 会造成像素偏移（C2）。`onPrimary` token 留给风格轴阶段统一处理。
2. **`.success` / `.warning` 的实心档用 `textPrimary`** —— 这两个色调此前**没有实心档用例**（无历史包袱），因此按底色亮度选取可读文字色：白字在 #27B15A / #F9B135 上对比度仅约 **2.8 : 1 / 1.9 : 1**，远低于 WCAG AA 的 4.5 : 1。
3. **`.success` 的浅底档用 `textPrimary`** —— 同色文字在 12% 浅绿底上仅约 3.0 : 1，不达标。`.done` 已于目视验收后改走实心档（见 §4.7 修正记录），但三维入口仍可构造出 `.soft + .success`，故规则保留。
4. **`.done` 的实心绿底同样用 `textPrimary`** —— 白字在 #27B15A 上仅 **2.8 : 1**，不达 WCAG AA。因此 `.filled + .success` / `.filled + .warning` 按底色亮度取近黑字，与 `.accent` / `.danger` 保持 `.white` 的策略不同。

> 这就是"三维模型允许 20 种组合"与"每种组合都要可读"之间的实际落差：**组合能力是模型给的，配色正确性仍要逐格判断**。未列出的格子尚无真实用例，将来用到时需单独评估。

**`.neutral + .filled` 为什么用 `colors.pageBackground` 做字色**：需要"反色"效果。`Color.primary.opacity(0.75)` 做底时——浅色模式下是深灰底，深色模式下是浅灰底。用 `pageBackground`（分平台自适应的页面底色）当字色，两种外观下都能得到正确对比度（浅色下白字，深色下黑字）。这是用既有 token 实现自适应的最简手段，无需新增 token。

### 4.2 背景色

| tone ＼ emphasis | `.filled` | `.outline` | `.soft` | `.plain` |
| --- | --- | --- | --- | --- |
| `.accent` | `colors.primary` | — | `colors.accentSoft` | — |
| `.neutral` | `Color.primary.opacity(0.75)` | — | `Color.primary.opacity(0.12)` | — |
| `.danger` | `colors.danger` | — | `colors.dangerSoft` ★ | — |
| `.success` | `colors.success` | — | `colors.successSoft` ★ | — |
| `.warning` | `colors.warning` | — | `colors.warningSoft` ★ | — |

★ = 本次新增的派生色（见 §五）。`—` 表示无背景（透明）。

### 4.3 描边

| emphasis | 描边颜色 | 描边宽度 |
| --- | --- | --- |
| `.outline` | 同 tone 的 `.soft` 前景色 | **`1.5`** ⚠️ |
| `.filled` / `.soft` / `.plain` | 无 | — |

⚠️ **描边宽度保持 `1.5`，不使用 `theme.stroke.hairline`（= 1）**。现有 `EDSSecondaryButtonStyle` 是 `1.5`，改用 token 会让所有描边按钮变细——**这是视觉变化，本次不做**。已在代码中标注为"历史值，待风格轴阶段统一"。

### 4.4 尺寸

| size | 视觉高度 | 横向内边距 | 圆角 | 字体 |
| --- | --- | --- | --- | --- |
| `.small` | `28` | `spacing.sm` = 12 | `radius.md` = 12 | `.bodyStrong` |
| `.regular` | **`theme.controlSize.buttonHeight`** = 34 | `spacing.md` = 16 | `radius.md` = 12 | `.bodyStrong` |
| `.large` | `44` | `spacing.lg` = 20 | `radius.md` = 12 | `.bodyStrong` |

**三个关键决定：**

1. **`.regular` 的高度必须读 token**（`theme.controlSize.buttonHeight`），不是硬编码 34。这样主题若改 `buttonHeight`，regular 档仍能跟随，且保证现有视觉零变化。
2. **`.small` / `.large` 用固定值 28 / 44**（不走 token）。理由：主题当前无 `buttonHeights` 数组，为一个未存在的扩展点引入"缩放系数"概念属过早抽象。已在代码注释中标注：若将来主题要支持多档 `buttonHeight`，此处需重新评估。
3. **圆角与字体三档统一**。尺寸档只改高与内边距，不改圆角——否则按钮形状会在切换 size 时跳变，破坏视觉一致性。

### 4.5 与最小可点区域的合并（既有行为，不改）

```
最终高度 = metrics.interactiveHeight(for: 视觉高度) = max(视觉高度, minimumInteractiveDimension)
```

`EDSResolvedMetrics`（7 个文件共享）**不动**，仅由按钮侧传入不同 `visualHeight`。

**已知副作用（既有行为，非本次引入）**：touch profile 下 `minimumTouchTarget` 通常为 44，因此 `.small`（28）在触屏设备上会被撑到 44——**与 `.regular` 在触屏下等高**。这是现有架构的既有设计（保证触屏可点面积），本方案沿用不改。

### 4.6 交互反馈（全部保持现状）

| 项 | 值 | 变化 |
| --- | --- | --- |
| hover 透明度 | `0.85` | 不变 |
| 禁用透明度 | `0.5` | 不变 |
| 按压缩放 | `0.97` | 不变 |
| 动效时长 | `0.15` | 不变 |
| 动效曲线 | `.easeInOut` | 不变 |
| reduceMotion 适配 | 有 | 不变 |

### 4.7 `.done` 的专属处理（D13）

`.done` 是唯一**自动注入图标**的 role：

```swift
// 调用方未显式传 systemImage 时，.done 自动补 checkmark
EDSButton("已完成", role: .done) { open() }
// 等价于 EDSButton("已完成", role: .done, systemImage: "checkmark") { open() }
```

**实现约束**：仅在 `role == .done` **且** `systemImage == nil` 时自动注入；调用方显式传入时以调用方为准。三维入口（签名 C）**不自动注入**——保持"原语不猜意图"的定位。

**图标语义与无障碍**：✓ 图标承担"已完成"的语义，使颜色不再是唯一线索（同时满足 `accessibilityDifferentiateWithoutColor`，与 `EDSBadge` 既有策略一致）。

#### D14 实施修正记录（2026-09-20）

杨哥在 Showcase 目视验收后反馈：12% 浅绿底太淡，"已完成"作为**可点击入口**体量不足。`.done` 改取**实心档**。

| | 原定（D14） | 修正后 |
| --- | --- | --- |
| 档位 | `soft + success + regular` | `filled + success + regular` |
| 背景 | `successSoft`（12% 浅绿） | `colors.success`（实心绿） |
| 文字 | `textPrimary` | `textPrimary`（不变） |
| 视觉重量 | 与 `.soft` 同级（弱） | 与 `.primary` 同级（强） |

**副作用及处理：**

- ✅ **意外收益**：与 `EDSBadge(.success)` 的混淆风险自动消失——不再只是底色深浅之差（V10 由"待观察"转为"通过"）。
- ⚠️ **需注意**：`.done` 现在与主操作 `.primary` 同权重。若在同一屏里大量使用 `.done`，会与主操作抢视觉焦点。**判断规则：只有"已完成状态本身需要被强调"时才用 `.done`**；仅表示"这里能点进去"的场景用 `.secondary` 即可。
- ✅ **兼容性**：`.done` 是本次新增 role，无历史用例，改档**不影响任何现有 App 的视觉**（与本文件 §六 的兼容性结论一致）。

## 五、新增 Token 清单

**全部为 `EDSColorTokens` 的派生计算属性，不新增任何 JSON 字段**（C4）。

| 新增属性 | 定义 | 用途 |
| --- | --- | --- |
| `successSoft` | `success.opacity(0.12)` | `.done` 背景；`success + .soft` |
| `warningSoft` | `warning.opacity(0.12)` | `warning + .soft` |
| `dangerSoft` | `danger.opacity(0.12)` | `danger + .soft` |

已存在、直接复用无需新增：`accentSoft`（= `accent.opacity(0.12)`，`EDSDesignTokens.swift:107`）。

**`.neutral + .soft` 的背景用 `Color.primary.opacity(0.12)` 现算**，不新增 `neutralSoft`——因为 `Color.primary` 是 SwiftUI 动态语义色，作为 token 属性会与"颜色一律 hex 存储、实例值可序列化"的既有约定冲突，而它又不需要被 App 覆盖。

**Codable 安全性核查**：`EDSColorTokens` 的 `CodingKeys` 显式声明为 5 项（`EDSDesignTokens.swift:128-130`），编解码只走这 5 个存储属性。派生计算属性**不参与编解码**，因此新增它们对 `EDSDefaultTheme.json` 与 `exportJSON()` 输出**零影响**。✅

## 六、兼容性验证（逐条，C1）

### 6.1 源码兼容性

| 现有写法 | 走哪条路径 | 结论 |
| --- | --- | --- |
| `EDSButton("确定", role: .primary) { }` | 签名 B | ✅ 不变 |
| `EDSButton("取消", role: .secondary) { }` | 签名 B | ✅ 不变 |
| `EDSButton("管理", role: .soft) { }` | 签名 B | ✅ 不变 |
| `EDSButton("删除", role: .danger) { }` | 签名 B | ✅ 不变 |
| `EDSButton("保存", systemImage: "checkmark") { }` | 签名 B | ✅ 不变 |
| `EDSButton { label }` （旧 label 版，省略 role） | 签名 A | ✅ 不变 |
| `EDSButton(role: .danger) { label }` | 签名 A | ✅ 不变 |
| `.buttonStyle(EDSPrimaryButtonStyle())` | 4 个旧 Style | ✅ 保留并转发 |
| 包内 `EDSEmptyState` / `EDSErrorState` / `EDSProgressPanel` / `EDSSidebarItemButton` / `EDSPill` 等调用方 | 签名 A / B | ✅ 不变 |

### 6.2 `Role` 新增 `.done` 的兼容性分析

`Role` 是 **非 `@frozen` 的 public enum**。Swift 对跨模块使用非 frozen enum 的规则：

- 外部模块 `switch` 它时，**本来就已被要求写 `@unknown default`**（否则只是 warning）；
- 新增 case **不会让原本能编译的代码变成错误**；

**结论：无破坏。** ✅

## 七、视觉变化清单（C2 的唯一例外）

### 唯一一项：D16 补齐 `.default` 预设的语义色

**现状**：`EDSPresetTheme.default`（`EDSTheme.swift:227-237`）只设了 `primary` / `accent` / `heroGradient`，**未设 `success` / `warning` / `danger`** → 落到 `EDSColorTokens()` 的默认值，即 SwiftUI 动态系统色。

**改动**：补上与 `.orange` 一致的 hex 值，使三个预设的语义色统一。

| Token | 改动前（`.default`） | 改动后 | 影响面 |
| --- | --- | --- | --- |
| `success` | 系统 `.green`（≈#28CD41） | `#27B15A` | `.done` 按钮、`EDSBadge(.success)`、所有用 `colors.success` 的组件 |

### ⚠️ 对现有 App 的实际影响（必须告知）

> **TTSMate / RightClickMate 使用 `.default`（蓝）主题时，"删除"按钮的红色会从系统红 #FF3B30 变为 #E54444。**

- **编译**：不受影响（不是 API 变更）✅
- **视觉**：会变化。红色略微偏暗、偏柔和，不再是系统标准红
- **iOS/macOS 外观切换**：系统色原本能随深浅外观微调，hex 为静态值 —— 这是既有架构的边界（§6.5 边界 3），本次不改变该性质

### 11.4 与计划的偏差（3 处，均为实施中发现的必要修正）

1. **`resolved` 签名去掉 `profile` / `horizontalSizeClass`** —— 原设计让解析器也参与算触控面积，但那是 `EDSResolvedMetrics` 的职责（7 个文件共享）。改为只依赖 `tokens`，纯函数更干净。已回写 §2.3。

2. **新增 `EDSButtonVisualBody`（原计划没有）** —— 原方案让 4 个旧 ButtonStyle 在 `makeBody` 里直接调用 `EDSButtonStyleCanvas.makeBody`。**这行不通**：`@Environment` / `@State` 只有在 `View` 上才会被注入，手动调 `makeBody` 拿不到环境值。因此把视觉逻辑抽成一个 `View`，各样式只传 `ButtonStyleConfiguration`。

3. **filled 档文字色分了两组（原 §4.1 表未分）** —— 实施时发现 `.success` / `.warning` 的实心档若照抄 `.white`，在 #27B15A / #F9B135 上对比度只有 2.8 : 1 / 1.9 : 1。这两个色调**无历史用例**，因此按亮度改用 `textPrimary`；`.accent` / `.danger` 保持 `.white` 以确保现有 App 零变化。已回写 §4.1。

### 11.5 目视验收后的修正（1 处）

4. **`.done` 由 `.soft` 改档为 `.filled`** —— 杨哥在 Showcase 目视后判定 12% 浅绿底"太淡"，作为可点击入口体量不足。已改档，并回写 §2.2 别名表 / §4.1 文字色规则 / §4.7 / §5 token 用途 / V9 验收标准。完整副作用分析见 §4.7 修正记录，核心一条：**`.done` 现与 `.primary` 同权重，只在"已完成状态本身需要强调"时使用。**
